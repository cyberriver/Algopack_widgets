# PRD: лаборатория гипотез FUTOI на доске FinamX

| Поле | Значение |
|---|---|
| Продукт | Личная лаборатория на виджетах Algopack + данные FinamX |
| Версия PRD | 1.1 |
| Статус | двухфазный эксперимент, денежная модель бэктеста и итоговый отчёт |
| Инструмент по умолчанию | SiZ6, 1 контракт; смена инструмента — новая сессия |
| Протокол | `Si_breakout_v0.3` (event time + первый `received_at` + M5-барьер) |
| Бюджет пилота | 15 000 ₽; формула — один из шлюзов, не единственный |
| Источники | `futoi_experiments_config.json`, `futoi_research_spec.md`, флоу заказчика, разборы 0.1–0.6, обсуждение 0.7 |

Документ задаёт вопрос исследования, протокол, модель данных, движок, экран и допуск к живой заявке.

### Что изменилось в 1.1

- Inline-форма бэктеста дополнена расчётным стартовым капиталом и фиксированным риском на одну сделку. Это модель для сравнения конфигураций, а не реальное исполнение.
- Для полного, настроечного и проверочного периодов считаются edge в R, Sharpe и Sortino по результатам сделок, доходность и денежный результат. Sharpe/Sortino масштабируются на √N сделок и не выдаются за годовые показатели.
- В «Результатах» эксперимент выбирается независимо из общего списка, включая завершённые.
- При завершении live-прогона фиксируется итоговый отчёт: период, выборка, win rate, edge, Sharpe, Sortino, net R, max drawdown и причины пропусков.
- Неактивная кнопка «Открыть» у завершённого эксперимента удалена. Карточка следует frequency-first: статус, инструмент и ключевые результаты видны сразу; технические параметры раскрываются по запросу.
- Денежный live-результат не выдумывается: до подключения исполнения, стоимости пункта и комиссий он явно помечен как недоступный.

### Что изменилось в 1.0

- Эксперимент состоит из двух раздельных прогонов одной неизменяемой конфигурации: `historical_replay` и `live_observation`. Исторические события и сделки никогда не дописываются в live-журнал.
- После выбора инструмента строится фактический профиль по истории: ATR14/20/28, ширина диапазонов 6/12/24 баров, частота пробоев, распределение adverse excursion, достижимость целей, длительность сделок и доступность OI.
- Каждое поле настройки показывает фактический диапазон, перевод выбранного значения в пункты/минуты и мягкое предупреждение о нереалистичном значении. Подсказка всегда содержит период и размер выборки.
- Подбор параметров и оценка результата разделены во времени: первая часть периода — calibration, последняя — holdout. Основной результат показывается по holdout; полный период служит диагностикой.
- Монитор позволяет выбрать несколько экспериментов и сравнить equity в R, drawdown, сделки, win rate, expectancy и причины пропусков. Backtest и live визуально разделены.
- Детектор всегда показывает текущий M5-бар, поддержку, сопротивление и расстояние до пробоя; отсутствие события больше не означает пустой экран.
- Самостоятельный widget «Методология» убран из навигации. Методология встроена в «Эксперименты»; старый URL остаётся alias для совместимости.
- Пользовательские названия: «Период формирования поддержки/сопротивления, баров» вместо «Окно уровней» и «Период измерения изменения OI, минут» вместо «Окно OI».
- ATR рассчитывается по Wilder RMA. Значение 20 остаётся baseline протокола, а не объявляется оптимальным; UI сравнивает 14/20/28.
- Для исторических данных настоящего `received_at` нет. Replay получает явный `latency_model_id=source_time_no_delay`; его нельзя интерпретировать как доказательство live-доступности данных.

### 0.1. Критерии приёмки версии 1.0

1. До создания draft пользователь видит профиль выбранного инструмента и подсказки у всех параметров стратегии.
2. Нереалистичное значение не блокируется молча: интерфейс показывает причину и фактический ориентир.
3. Backtest запускается для draft, сохраняет период, latency model, calibration/holdout split, equity и метрики.
4. Один эксперимент хранит replay и live отдельно и показывает расхождение результатов.
5. Монитор переключает основной эксперимент и накладывает до четырёх выбранных экспериментов на один график сравнения.
6. При нуле пробоев детектор показывает рынок и расстояние до уровней.
7. Исторический backfill не создаёт live-сделок и не меняет `received_at` live-пакетов.
8. «Настроить бэктест» открывает inline-форму точного периода от 5 до 60 календарных дней, долей «период настройки / проверочный период» и модели доступности; запуск показывает выполнение, успех или ошибку рядом с нажатой кнопкой.
9. Все действия имеют pressed/focus/busy-состояния. Асинхронная кнопка меняет подпись до завершения операции.
10. График сравнения подписывает X как календарные дату/время, Y как накопленный R и предупреждает, когда кривые совпадают из-за идентичных конфигураций.
11. Монитор показывает не менее 60 последних M5-свечей, текущие уровни и события выбранных экспериментов. Маркеры различают ценовой пробой, подтверждение OI, отказ фильтра и технический пропуск; по клику открывается карточка факта.
12. Под графиком есть отдельная дорожка каждого сравниваемого эксперимента. Цвет не кодирует будущую прибыльность: исход сделки показывается только в карточке события.
13. Бэктест показывает edge, Sharpe, Sortino, доходность и прибыль в рублях с явными капиталом и риском на 1R.
14. Завершение эксперимента создаёт неизменяемый итоговый live-отчёт; завершённый эксперимент выбирается в «Результатах», а не повторно «открывается» из карточки.
15. Низкочастотные технические поля карточки скрыты в progressive disclosure, основные статус, конфигурация, результаты и действия доступны без перехода на другой экран.

### Что изменилось в 0.9

- Лаборатория сведена к четырём Open Platform widgets: **Эксперименты**, **Методология**, **Монитор**, **Результаты** (в 1.0 методология переносится внутрь экспериментов).
- Collector Algopack общий; несколько экспериментов работают параллельно со своими неизменяемыми конфигурациями, событиями и книгами сделок.
- Инструмент, условие входа, параметры, режим исполнения и лимит капитала задаются при создании эксперимента.
- Пользовательские названия вариантов: **«Пробой цены»** и **«Пробой цены + рост OI»**; внутренние id сохраняются только в данных.
- Реальный режим можно описать в draft, но запуск заблокирован до Trade API, расчёта ГО/лотности и явного подтверждения пользователя.

### Что изменилось в 0.8

- Для tradestats и FUTOI раздельно сохраняются `source_time` и первый `received_at`.
- Решение по M5 принимается барьером не позже `bar_end + decision_deadline_ms`.
- Причины разделены: `price_received_late`, `oi_received_late`, `processing_late`, `oi_unavailable`.
- `processing_late` означает задержку worker после готовности пакетов, а не возраст биржевого бара.
- Вход берётся только из первого M5-бара, начавшегося после `decision_time`; исторический open не используется задним числом.

### Что изменилось в 0.7

- Добавлены экраны **методологии** и **реестра гипотез**; наблюдение связывается с гипотезой, не с вердиктом на графике.
- OI: последний снимок *до* бара **не выбрасываем**. Рядом пишем возраст и lifetime. `oi_unavailable` — только если снимка нет вовсе.
- ΔOI в протоколе — `ln(OI_now / OI_ref)`; в факте храним также разницу в контрактах.
- Инструмент можно менять (`fdc3.instrument` + вселенная FUTOI). Смена = новый журнал, прогрев заново. `finamx.timeframe` не слушаем.
- Позиции: не форкаем виджет ФинамХ. На доску ставим `com.tradingdiary.positions-table`; у нас переключатель «виртуальный / мой».
- Шарп и Сортино — по виртуальной книге, с N и окном. Не вердикт.
- Ручная сделка — `manual_analysis`, не вход детектора.
- Цена и FUTOI только **Algopack APIM** (`getSeries`, Super Candles `fo/tradestats`). `iss.moex.com` не источник лаборатории.

## 1. Зачем это

Не робот. Лаборатория: одни и те же правила фиксируют пробои, доступный OI, решение и результат. Зависимость ищут в таблице, включая пропуски и убытки.

### 1.1. Исследовательский вопрос

> Какова добавочная ценность фиксированного 15-минутного изменения OI для семейства пробойных стратегий, параметры которых заданы в барах соответствующего ТФ?

«Добавочная ценность» — отличие исходов одной и той же ценовой стратегии «с фильтром OI» и «без него» на одинаково определённых событиях.

Два разных аналитических результата, их нельзя подменять:

| Результат | Выборка | Зачем |
|---|---|---|
| Вклад фильтра | Только события с доступным OI (`oi_status ≠ unavailable`) | Чистый эффект правила ΔOI > 0 |
| Рабочая система | Все ценовые события, включая пропуск `oi_unavailable` | Что получит оператор, когда источник OI молчит |

Отказ FUTOI не должен выглядеть как полезное действие фильтра.

### 1.2. Ограничение сравнения ТФ

Сравнение ТФ **не изолирует** влияние одной частоты свечей. Вместе с периодом бара меняются диапазон, ATR, буфер, длина удержания и момент решения относительно сессии.

- **M5 — основной подтверждающий эксперимент.**
- **M15, M10, M30, H1 — исследовательские тени.** Не обязательство P0, не live-ветка в v0.1.
- **D — только контекст.** Без виртуальных сделок: дневной бар закрывается после сессии, перенос позиции запрещён.
- Мульти-ТФ архитектуру не удаляем. Шесть ТФ не делаем равноправным P0.

События разных ТФ и несколько пробоев одного дня не независимые подтверждения. Связь — `market_episode_id`. Неопределённость — кластер по торговым дням.

### 1.3. Этапы исследования

| Этап | Что проверяем | Деньги |
|---|---|---|
| A. Процесс | Детектор, часы, join FUTOI, виртуальные сделки | нет |
| B. История | Тот же движок на прошлом периоде, holdout | нет |
| C. Исполнение | Цена, комиссия, проскальзывание, стоп, сверка | 1 контракт после отдельного допуска |

Журналы не смешиваются. «30 событий» — плашка UI, не допуск к выводу и не допуск к торговле. Поставка — §16.

### 1.4. Что человек хочет проверить (простыми словами)

1. Есть ли движение по **выбранному** инструменту.
2. Видно ли это движение в открытом интересе.
3. Было ли **пробитие** зоны поддержки / сопротивления (close за U+b / D−b).
4. Подтвердилось ли пробитие ростом OI.

Эти четыре вопроса — не кнопки на графике, а **гипотезы** §1.5. Строка в наблюдениях может быть связана с одной или несколькими.

### 1.5. Реестр гипотез

Каждая гипотеза: `hypothesis_id`, утверждение, чем мерим, статус (`open` \| `watching` \| `abandoned`). Связь с событием — слой аннотаций `hypothesis_ids[]`. Смена статуса гипотезы не переписывает факт и не создаёт вердикт «подтверждена» на холсте.

| id | Утверждение | Чем мерим | Не путать с |
|---|---|---|---|
| `H-MOVE` | По выбранному инструменту есть направленное движение / расширение диапазона | факт события B, ширина U−D, ATR | «надо входить» |
| `H-OI` | Это движение видно в OI | знак и величина ΔOI, `futoi_age` | вход B1 |
| `H-BRK` | Close за U+b / D−b — пробой зоны, а не шум внутри диапазона | факт B0 + `quality_review` | глаз на графике ФинамХ |
| `H-CONF` | Пробой с ΔOI > 0 лучше цены одной | вклад фильтра B1 − B0 только на **свежем** OI (`oi_fresh`) | дни без пакета и корзина `stale` |

Других id в v0.2 нет. Новую гипотезу добавляют явно (новая строка реестра), не подписью в заметке.

Связать наблюдение с гипотезой можно в W5 и в W11. Отвязать — тоже. Это не исключает строку из `primary_analysis`.

| Тема | Решение |
|---|---|
| Вопрос | Добавочная ценность фиксированного 15-мин ΔOI |
| Гипотезы | H-MOVE, H-OI, H-BRK, H-CONF; связь со строкой, не вердикт |
| Роли ТФ | M5 основной; тени; D — глаз |
| Инструмент | Меняется человеком; на сессию заморозка; шина `fdc3.instrument` |
| Готовность | Три лампы: `price_ready`, `oi_ready`, `execution_ready`. Нет снимка OI ≠ нет события |
| Шина `finamx.timeframe` | Не слушать |
| Детектор | Серверный worker. Виджет не владеет сделкой |
| Сентимент | Вне scope |
| Факты | Не правятся на месте. Исправление = ревизия с `supersedes_id` |
| Аналитический запуск | Закрепляет факты **и** состав выборки (`analysis_run_id`) |

| Ручные строки | Не в `primary_analysis` |
| Оценка строки | `quality_review` + `research_note`. Вклад фильтра — формула |
| Горизонт | В средние только `complete`. `truncated` рядом, не как полные 60 минут |

| Replay | `availability_basis` + `latency_model_id`. Без live `received_time` — симуляция, не копия сессии |
| Восстановление | Вовремя сохранённый пакет можно досчитать. Поздний пакет — не вход по старой цене |
| Live-ветка | `live_variant = unset` |
| Токен | На BFF. Выход ≠ удаление секрета ≠ закрытие позиции |
| Бюджет | Формула + независимые шлюзы |

## 3. Протокол `Si_breakout_v0.3`

Смена любого обязательного поля повышает версию и открывает новый журнал.

### 3.2. Три лампы готовности

Отсутствие OI ≠ невозможность наблюдать цену. Красный FUTOI не гасит ценовой журнал.

| Лампа | Зелёная когда | Красная значит |
|---|---|---|
| `price_ready` | закрытые бары ТФ идут, часы согласованы, прогрев 12+20 есть, серия верна | нельзя обнаружить пробой |
| `oi_ready` | пакет FUTOI не старше 10 мин, обе группы вместе | нельзя проверить фильтр; событие всё равно пишем |
| `execution_ready` | `price_ready` + шлюзы §12 + (если `live_variant` требует OI — ещё `oi_ready`) + секрет на BFF | нельзя допустить живую заявку |

Поведение движка:

| Состояние | Событие | `B_PRICE` | `B_OI_POSITIVE` |
|---|---|---|---|
| Цена готова, есть снимок до бара | Записываем; кладём OI, `futoi_age`, `oi_fresh` | Считаем | ΔOI > 0 → вход; иначе skip `filter` |
| Цена готова, снимка нет вовсе | Записываем, `oi_status = unavailable` | Считаем | Skip `oi_unavailable`, PnL = 0 |
| Цена готова, снимок есть, но `futoi_age` > 10 мин | Записываем, `oi_fresh = false` | Считаем | Фильтр по ΔOI как обычно; **не** в среднее вклада фильтра |
| Цена не готова | Пишем покрытие `coverage_gap`, не событие пробоя | Не считаем | Не считаем |

Простым языком: **`B1 = oi_unavailable`** — пробой по цене был, а **открытого интереса не было ни одного** (пакет не приходил). Это не «фильтр отказал». Фильтр отказал — это skip `filter`: OI посчитали, ΔOI не больше нуля. Старый, но существующий снимок — не `unavailable`, а строка с возрастом.

`coverage_gap` — отдельная сущность (ТФ, интервал, причина), не строка пробоя и не «фильтр отсёк».

Для теней лампы независимы. D ламп детектора не имеет.

| Термин | v0.1 |

### 3.5. OI

Биржа / Algopack публикует FUTOI **раз в 5 минут**. Наш перезапрос чаще (тик лаборатории ~30 с) не создаёт новую цифру — он обновляет только `futoi_lifetime`.

**OI одного снимка** = лонги физлиц + лонги юрлиц (`L_FIZ + L_YUR`).

Два снимка, оба строго **раньше начала** сигнального бара (`available_time < bar_start`):

| Снимок | Как берём |
|---|---|
| `OI_now` | последний такой пакет, какой есть. Не выбрасываем из‑за возраста |
| `OI_ref` | последний пакет на момент `OI_now.time − 15 мин` (окно `oi_window`). Если ближе нет — ближайший более старый, факт интервала пишем |

**ΔOI (правило фильтра B1)**

\[
\Delta\mathrm{OI} = \ln(\mathrm{OI}_{now} / \mathrm{OI}_{ref})
\]

Вход B1 только если ΔOI **> 0**. Ноль и минус → skip `filter`.

В факте всегда храним ещё `oi_now`, `oi_ref`, `oi_change_contracts = OI_now − OI_ref` (то, что сейчас показывает таблица). Движок v0.6 считал только разность; v0.2 фильтрует по логарифму, разность оставляет для чтения. Знаменатель ≤ 0 → признак отсутствует (`unavailable`), не ноль.

**Почему «не увидели» OI**

- пакета ещё не было в сессии;
- пакет в том же слоте, что бар, или позже — его нельзя брать (подглядывание);
- APIM не ответил;
- выкинуты слоты 23:40 / 23:50;
- вечерняя сессия вне протокола.

Раньше (черновик 0.6) снимок старше 10 минут тоже становился `unavailable`. **Так больше не делаем.**

**Возраст и lifetime — два разных часа**

| Поле | Смысл | Единицы |
|---|---|---|
| `futoi_asof` | `tradetime` пакета на бирже | время Москвы |
| `futoi_age_sec` | `bar_start − futoi_asof` | минуты и секунды в UI (`mm:ss`) |
| `futoi_lifetime_sec` | «сейчас» минус время последнего **успешного** ответа APIM | минуты и секунды; обновляется на каждый перезапрос |
| `oi_fresh` | `futoi_age_sec ≤ oi_fresh_max_age_min × 60` | да / нет |
| `oi_status` | `available`, если есть хоть один снимок до бара; иначе `unavailable` | |

`futoi_lifetime` кормит лампу `oi_ready` (поток жив). `futoi_age` кормит исследование H-CONF и корзины сводки.

Поздний пакет в уже записанное событие **не дописывается**.

Поля каждой точки:

| Поле | Смысл |

| `target_time` | `signal_time + offset` (часы) или `bar_end` n-го бара |

`truncated` — упёрлись в конец сессии, записали последний тик. Полезная запись, **не** полноценные 60 минут.

В стандартной сводке горизонта:

- средняя доходность — только `complete`;
- число `truncated` и `unavailable` — рядом;
- укороченные — отдельный показатель (доходность на `actual_elapsed_seconds`), не в среднее «через 60 минут».

`event_id`: `SI_B_M5_001`. Ключ: `(protocol_id, contract, timeframe, bar_end, kind, direction, mode)`. `parent` — тот же ТФ. `market_episode_id` — кластер дня, не слияние строк.

### 3.10. Смена инструмента

Вселенная — тикеры FUTOI (`Si`, `BR`, `RI`, …). Торговая серия — фронт-месяц Super Candles (для Si по умолчанию SiZ6). На сессию серия заморожена.

Человек меняет инструмент в W12 или кликом, который публикует `fdc3.instrument` (фильтр FUTOI, таблица позиций ФинамХ). Лаборатория **подписывается** на `fdc3.instrument`. `finamx.timeframe` не слушает.

Смена семейства или серии:

- закрывает текущий журнал сессии;
- сбрасывает прогрев 12+20 баров;
- не переносит U/D/ATR и открытую виртуальную сделку на новый тикер;
- создаёт `session` с новым `contract` / `family`.

Смена «потому что сегодня ликвиднее» посреди сессии — осознанное действие с подтверждением.

### 3.11. Шарп и Сортино

Считаем по **виртуальной** книге варианта (закрытые сделки), не по глазу.

- Доходность шага — net R закрытой сделки или дневная сумма R (в отчёте указать, какая).
- Шарп: среднее / σ всех шагов. Безрисковая — 0, пока не зададим явно.
- Сортино: среднее / σ только отрицательных шагов.
- Рядом обязательны: N, окно дат, `protocol_id`, `analysis_run_id`.
- N < 30 — качественный ориентир, не ставка «с точностью».
- «Мой портфель» хоста **не** даёт историю equity. Шарп живого счёта без своей кривой не считаем и не подменяем виртуальным.

## 4. Слои данных и аналитический запуск

Факты иммутабельны. Аннотации не меняют PnL. Исправление — новая ревизия с `supersedes_id`.

`quality_review`: `not_reviewed` \| `valid` \| `data_issue` \| `protocol_issue`.

Вклад фильтра **на событиях с доступным OI**:

\[
\Delta\mathrm{PnL}_i = \mathrm{PnL}_{B\_OI\_POSITIVE,i} - \mathrm{PnL}_{B\_PRICE,i}
\]

Пропуск → PnL варианта = 0. События `oi_unavailable` в эту среднюю **не входят**. Они входят в метрику «рабочая система».

### 4.1. Закрепление запуска

Одна `data_revision_id` после смены `quality_review` даёт другой знаменатель. Поэтому отчёт несёт:

| Поле | Зачем |
|---|---|
| `analysis_run_id` | первичный ключ отчёта |
| `data_revision_id` | какие факты |
| `annotation_revision_id` | какой набор `quality_review` |
| `protocol_id` | какие правила |
| `engine_version` | какой код движка |
| `selection_policy` | например `primary_detector_not_excluded` |
| `cost_model_id` | базовые издержки или ×2 |
| `availability_basis` / `latency_model_id` | если replay |

UI сложный не нужен: «сохранить отчёт» пишет этот набор. Пересчёт без тех же исключений — другой `analysis_run_id`.

В отчёте отдельно: число исключённых событий и причины (`data_issue`, `protocol_issue`, `manual`, `oi_unavailable` для вклада фильтра). Качество данных не должно быть неявным отбором.

`primary_analysis`: `source=detector` и политика выборки запуска. Ручное — только `manual_analysis`.

```

```

### 6.1. Replay и доступность

| `availability_basis` | Когда |
|---|---|
| `recorded_live_receipt` | Сравнение replay с живым журналом: то же `received_time`, что записали в live |
| `source_publication_time` | В пакете есть документированное время публикации, live-получения нет |
| `modeled_publication_delay` | Нет ни того, ни другого; задержка из `latency_model_id` |

Обязателен `latency_model_id` на любом историческом прогоне.

Сравнение «replay = live» допустимо только на `recorded_live_receipt`. Иначе отчёт маркируется: **историческая симуляция с допущением о задержке**, не точное воспроизведение сессии.

### 6.2. Восстановление после сбоя

| Случай | Можно | Нельзя |
|---|---|---|
| Пакет **сохранён вовремя**, worker не успел | Пересчитать, сохранив фактический `processing_delay_ms`. Если delay ≤ `max_signal_processing_ms` — обычный вход. Если больше — событие есть, trade skip `processing_late` | Выдавать позднюю обработку за своевременный вход |
| Пакет **впервые получен поздно** | Записать событие с OI по факту доступности **сейчас** и `futoi_age`; trade по исторической цене входа не открывать | Создать сделку «как будто котировка тогда была» |
| «Что должно было произойти» | Отдельный `historical_replay` | Чинить live-журнал |

Красный `price_ready` задним числом в live не добираем. Догон — только вовремя лежащие в хранилище пакеты.

Прочие сценарии: вкладка закрыта — worker жив; две доски — один ключ; повтор бара — идемпотентность; FUTOI задержался — берём последний снимок до бара, пишем `futoi_age`; `oi_unavailable` только если снимка нет; ожидание F2 на worker.

### 6.3. Просадка

В интерфейсе **разные имена**:

| Показатель | Считается по |
|---|---|
| `closed_drawdown` | только закрытые сделки варианта |
| `mark_to_market_drawdown` | закрытые + переоценка открытых |

Не подписывать оба словом «просадка». Торговая статистика по умолчанию показывает оба, акцент на `closed_drawdown`.

### 8.14. Пользовательские сценарии

Человек на доске — наблюдатель и редактор пометок. Детектор, виртуальные сделки и (после допуска) заявки делает worker. Ниже: что делать на каждом виджете, чего не делать, куда идти дальше.

#### Сквозные сценарии дня

| Когда | Что делает человек | Где |
|---|---|---|
| Один раз, до первой сессии | Читает методологию, создаёт протокол, смотрит гипотезы, не трогает F-поля без нужды | W10, W11, W1, при смене F — W9 |
| Перед сессией | Выбирает инструмент, смотрит три лампы M5 и lifetime. Цена красная — не ловит глазом. OI жёлтый — сессию ведёт, B1 не равен «нет фильтра» | W12, W2, график M5 ФинамХ |
| Во время сессии | Смотрит маркеры на W3/W4, не жмёт вход. Комментарий и качество — в таблице | W3, W4, W5 |
| После сессии | Проверяет полноту строк, ставит `quality_review`, сохраняет отчёт. Не меняет правила под увиденное | W5, W6 |
| Раз в несколько сессий | Смотрит вклад фильтра vs рабочую систему, truncated отдельно. Плашка «< 30» — не вывод | W6 |
| Этап B | Запускает replay, сравнивает с live, не чинит live-строки | W1/W6 команда replay, W5 журнал replay |
| Этап C / P3 | Вводит секрет, смотрит ГО и шлюзы, сверку. Не подтверждает заявку | W8, W7 |
| Этап C / P4 | Записывает `live_variant`, подтверждает один черновик, следит за «заявка ≠ позиция» | W1, W8, W7 |
| Уход с доски | Сворачивает виджет или запрещает входы. Секрет не удаляет, если есть позиция | W8 |

#### Уже стоят на доске (не новые)

**Фильтр FUTOI.** Выбрать семейство и серию, заморозить на сессию. Смена через W12 с подтверждением. Сброс прогрева. Публикует `fdc3.instrument`.

**Графики ФинамХ (D…M5).** Смотреть режим. Таймфрейм в карточке не менять через общую шину. По D не ждать сделок лаборатории. Не считать пробой «на глаз» вместо строки в W5.

**OI / направленные / лонг-шорт.** Контекст толпы. Не вход и не вердикт. Расхождение с маркером W3 — повод к заметке в W5, не к ручной сделке.

#### W1 — Протокол

Зачем заходит: понять, какие правила сегодня заморожены; завести v0.1; когда нужно — клонировать версию.

Делает: читает серию, ТФ, ночь, окно OI, реестр. Если правило изменилось — «Скопировать в v0.2», пишет причину, закрывает старый журнал. Перед P4 — явно ставит `live_variant` (до этого видит `unset`).

Не делает: не правит серые поля «на пять минут»; не выбирает live-ветку «потому что сегодня B1 красиво отработал».

Дальше: W2, если сессия сейчас; W9, если меняет только F.

#### W2 — Готовность

Зачем: решить, ведётся ли журнал, и не путать «нет OI» с «нет цены».

Делает: перед открытием и после обрыва смотрит лампы M5. Зелёная цена + жёлтый OI → работает как обычно, в уме помечает «B1 сегодня часто skip». Красная цена → не торгует глазом, смотрит `coverage_gap`. Серое исполнение до P4 — норма.

Не делает: не «чинит» красную лампу сменой ТФ; не запускает день, если не уверен в серии и часах.

Дальше: при зелёной цене — W3; список дыр — сверить с W5 в конце дня.

#### W3 — Лаборатория B

Зачем: видеть, что детектор увидел пробой, какие ветки в рынке или в skip.

Делает: переключает ТФ локально (по умолчанию M5). Смотрит U/D, маркер, карточку: B0 вошёл, B1 пропустил почему. Открывает строку в таблице, если нужна заметка.

Не делает: не входит вручную, не отменяет автособытие, не ставит вердикт «OI помог», не ждёт подтверждения гипотезы на графике.

Дальше: возврат цены — W4; пометка — W5.

#### W4 — Лаборатория F

Зачем: видеть цепочку ложного пробоя и что F2 ещё ждёт подтверждение.

Делает: смотрит таймер F2 (он с сервера). Если skip `max_initial_risk` — читает бейдж, не двигает стоп на графике. Переходит в W9 только чтобы понять числа, не чтобы подкрутить под текущий эпизод.

Не делает: не присваивает F2 цену входа F0; не закрывает вкладку с мыслью, что ожидание умрёт (оно не умрёт — но и торопить его нельзя).

Дальше: W5 для связи с родительским `SI_B_*`.

#### W9 — Параметры F

Зачем: прочитать, почему стоп от экстремума, и только сознательно сменить протокол.

Делает: читает пояснения. Если меняет окно или потолок риска — создаёт v0.2 с причиной.

Не делает: не подгоняет стоп под открытый сейчас эпизод; не ждёт, что v0.1 перепишется тихо.

Дальше: W1 показывает новую версию, старый журнал закрыт.

#### W5 — Наблюдения

Зачем: единственное место работы с журналом: смотреть факты, помечать качество, выгружать, заводить ревизию.

Делает:

- в сессии — фильтр M5 + сегодня, проверяет, что пробой стал строкой;
- ставит `quality_review`, гипотезы и заметку («бар кривой», «сам чуть не пропустил глазами»);
- если факт ошибочен — «Завести ревизию» с причиной, не правит close в ячейке;
- ручная строка — только «детектор молчал, вот дыра», понимает что в primary не попадёт;
- в конце дня — XLS или «Сохранить отчёт».

Не делает: не выкидывает убыточные строки из primary «чтобы сводка красивее»; не дописывает поздний OI в старое событие; не считает одну прибыльную B1 доказательством.

Дальше: W6 с тем же `analysis_run_id`.

#### W6 — Сводка

Зачем: смотреть накопленное, не отдельный пробой.

Делает: вкладка «События» — корзины ΔOI, `stale`, `unavailable`, только `complete` в средних. Вкладка «Стратегии» — вклад фильтра только `oi_fresh`, рабочая система — все B0. Вкладка «Риск» — Шарп/Сортино с N. Вкладка «Отчёты» — старый запуск. При «< 30» читает плашку как «рано».

Не делает: не складывает M5 и H1 в одну победу; не назначает `live_variant` из этой карточки.

Дальше: если хочет live — сначала P2 replay и допуск, потом W1 + W7 + W8.

#### W7 — Шлюзы

Зачем: понять, пустит ли система живой вход, и почему 15 000 ещё не значит «можно».

Делает: сверяет формулу, ГО, риск стопа, дневной убыток. Если `trade_risk_gate` красный — не ищет обход в W8. Жёлтый OI при зелёной цене — читает «виртуальный B0 идёт», не «всё сломалось».

Не делает: не двигает `reserve_buffer` в сессии, чтобы шлюз позеленел (это новая версия протокола).

Дальше: зелёные шлюзы и записанный `live_variant` — черновик в W8.

#### W8 — Исполнение

Зачем: отдать секрет BFF, видеть счёт, позже подтвердить одну заявку, корректно отключиться.

Делает:

- P3: вводит секрет, проверяет `account_id`, смотрит сверку, не жмёт «подтвердить»;
- P4: читает черновик (счёт, серия, сторона, qty, цена), подтверждает, пока TTL жив; если черновик изменился — подтверждает заново;
- уходит с доски кнопкой «свернуть» или «запретить входы»;
- удаляет секрет только после диалога, если нет позиции, либо явно принимает «сопровождать больше не будем».

Не делает: не жмёт четыре команды как один «выход»; не считает «заявка принята» открытой позицией; не удаляет секрет, чтобы «закрыть сделку»; не отправляет заявку при `live_variant = unset` (кнопки нет).

#### W10 — Методология

Зачем: вспомнить правила без чтения серых полей W1.

Делает: читает B0/B1, ΔOI, три причины «B1 не вошёл». Открывает, когда сомневается, что такое `oi_unavailable`.

Не делает: не правит текст как протокол.

Дальше: W11, W5.

#### W11 — Гипотезы

Зачем: видеть, какие утверждения проверяем, и сколько строк к ним привязано.

Делает: ставит статус `watching`, из карточки прыгает в связанные события. Связывает/отвязывает id.

Не делает: не жмёт «гипотеза подтверждена».

Дальше: W5, W6 вклад фильтра только для H-CONF.

#### W12 — Инструмент

Зачем: сменить семейство и серию сознательно.

Делает: выбирает Si/BR/…, подтверждает смену, ждёт прогрев.

Не делает: не меняет тикер каждый час «потому что дёргается».

Дальше: W2, W3.

#### W13 — Портфель

Зачем: не путать виртуальный 1 контракт и брокерский счёт.

Делает: смотрит virtual B0/B1. Для «мой» открывает готовый виджет позиций или ждёт `portfolio.read`.

Не делает: не складывает две книги; не вставляет Trade API токен в лабораторию.

#### W14 — Риск

Зачем: увидеть Шарп/Сортино виртуальной книги с честным N.

Не делает: не назначает live из «Шарп 1.2 на 8 сделках».

#### W15 — Ручная сделка

Зачем: записать, что сам взял или пропустил, не подменяя детектор.

Делает: заполняет форму к событию или без него.

Не делает: не ждёт, что ручная строка попадёт в primary и во вклад фильтра.

#### Replay (команда, не отдельный виджет)

Зачем: проверить, что движок на истории даёт те же события, что правила.

Делает: запускает из W1/W6, видит журнал `historical_replay` и базис доступности. Если нет live `received_time` — читает маркер «симуляция», не «повтор сессии».

Не делает: не переносит строки replay в live-таблицу и не чинит ими сегодняшний день.

## 9. Потоки

**Пробой при живой цене.** Есть `price_ready` → событие. Снимок OI есть — считаем ΔOI и age. Снимка нет — `B_PRICE` считается, B1 skip `oi_unavailable`. Снимок старший 10 мин — B1 по ΔOI, вклад фильтра не берёт.

**Наложение.** Событие есть. Открыта сделка того же варианта → skip `position_already_open`.

**Сессия кончается.** Событие есть, новый вход skip `session_close`, открытое flatten, горизонты `truncated` и не в среднее complete.

**Ложный пробой.** 3 бара → F0 → F1 при росте стороны от снимка до `bar_start` → ожидание F2.

**Replay.** Тот же код, другой журнал. Без recorded receipt — симуляция.

**Допуск C.** `live_variant ≠ unset`, шлюзы, `analysis_run_id`, отметка допуска.

## 11. Вклад фильтра

Вклад фильтра считается только где `oi_status = available` **и** `oi_fresh`. Корзина `stale` (снимок есть, age > 10 мин) и `unavailable` (снимка нет) в эту среднюю не входят. Рабочая система = все `B_PRICE` события с `price_ready`, включая stale и дни без FUTOI. Кластер — торговый день.

## 12. Шлюзы

Формула 15 000 и шесть шлюзов без изменения смысла. `data_quality_gate` красный при несвежей **цене** или при `live_variant`, которому нужен OI, и красном `oi_ready`. Красный OI **не** запрещает виртуальный B0.

## 13. Машина исполнения

Без изменений по состояниям: `DRAFT → … → CLOSED` плюс `REJECTED`, `UNKNOWN`, `RECONCILIATION_REQUIRED`. Идемпотентность, таймаут ≠ отказ, fill без защиты — авария.

## 14. Подключение, выход, секрет

Секрет и JWT — на BFF, не в `localStorage`. Это **не** четыре имени одной кнопки.

| Действие | Секрет | Новые входы | Открытые живые позиции / заявки |
|---|---|---|---|
| Выход из интерфейса | остаётся | по текущим шлюзам | worker сопровождает |
| Запрет новых входов | остаётся | нет | сопровождаются |
| Отключение брокера | остаётся, вызовы наружу стоп | нет | **нельзя** молча бросить: экран открытого + выбор: оставить сопровождение (секрет нужен) или отказ отключать |
| Удаление секрета | стирается вместе с JWT | нет | **запрещено**, пока на этом счёте есть позиция или заявка лаборатории, либо человек явно подтвердил: «сопровождение прекращаю, позицию не закрываю» |

Удаление секрета **не** закрывает позицию и **не** шлёт flatten. Перед ним W8 показывает список открытого: символ, сторона, qty, заявки, кто будет сопровождать (этот BFF / никто).

Автоматически считать logout закрытием нельзя.

Аудит: `ui_leave`, `entries_halted`, `broker_disconnect_requested`, `secret_cleared`, без тел секрета.

## 18. Критерии приёмки

Движок:

1. Replay с тем же входом, протоколом, `availability_basis=recorded_live_receipt` → те же события.
2. Replay без live receipt помечен как симуляция с `latency_model_id`.
3. Будущий FUTOI не меняет прошлое решение.
4. Нет снимка OI → событие и `B_PRICE` есть; B1 = `oi_unavailable`. Есть снимок старше 10 мин → OI в факте, `oi_fresh=false`, вклад фильтра не берёт. ΔOI ≤ 0 при наличии снимка → skip `filter`, не `oi_unavailable`.
5. Нет цены → нет пробоя, есть `coverage_gap`.
6. Две вкладки не дублируют сделки.
7. Вовремя сохранённый пакет после сбоя worker досчитывается с `processing_delay_ms`; просрочка — `processing_late`, не «вовремя».
8. Пакет получен поздно — нет входа по исторической цене.
9. Ручные строки не в primary.
10. Исправление не уничтожает факт.
11. M10: границы и дыра одной M5.
12. Стоп+тейк в одном OHLC → стоп первым.
13. Сигнал у cutoff → §3.4.
14. Открыта сделка варианта → новое событие, trade `position_already_open`.
15. Среднее «через 60 минут» только по `complete`; truncated посчитаны отдельно.
16. Сохранённый отчёт несёт набор §4.1; смена `quality_review` без нового `analysis_run_id` старый отчёт не подменяет.
17. D без виртуальных сделок.
18. Две просадки подписаны по-разному.

Продукт:

19. На графике нет вердикта.
20. P0–P3 без SUBMITTING.
21. Живая заявка только при `execution_ready`, `live_variant`, шлюзах и свежем подтверждении.
22. Таймаут ≠ отказ; fill без защиты — авария.
23. Выход из UI не удаляет секрет и не закрывает позицию.
24. Удаление секрета при открытой позиции требует явного сценария §14, не flatten.
25. Секрет не в `localStorage`.
26. Наблюдение можно связать с H-MOVE / H-OI / H-BRK / H-CONF без кнопки «подтверждена».
27. Смена инструмента закрывает журнал и сбрасывает прогрев.
28. W13 virtual ≠ host; host не рисует свою таблицу позиций.
29. Шарп/Сортино показывают N и отказываются быть выводом при N < 30.
30. `futoi_age` и `futoi_lifetime` в UI как `mm:ss`, обновление lifetime на успешный перезапрос.
